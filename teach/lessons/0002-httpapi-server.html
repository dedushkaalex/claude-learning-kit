Сервер из контракта: HttpApi от схемы до порта

Один конкретный результат: после урока ты по любому входящему запросу к todo-серверу называешь, какой слой его обработает, какая схема его проверит и какой статус уйдёт в ответ, не запуская сервер.

Связь с проектом: это шаги 1–3 фазы 8. Файлы: src/entities/todo/todoApi.ts (контракт), todoHandlers.ts (реализация), src/server/main.ts (запуск). Тесты: __tests__/todoApi.test.ts и __tests__/todoHandlers.test.ts.

1. Четыре слоя, снизу вверх

Сервер на HttpApi собирается из четырёх значений, и каждое следующее оборачивает предыдущее. Порядок здесь не стиль, а требование типов.

  1. Контракт. HttpApi.make("todoApi").add(HttpApiGroup.make("todo").add(...endpoints)). Чистые данные: пути, методы, схемы params, payload, success, error. Ни одного эффекта.
  2. Обработчики. HttpApiBuilder.group(todoApi, "todo", (handlers) => handlers.handle("create", ({ payload }) => createTodo(payload.title))...). Это Layer, и TypeScript следит, чтобы каждое имя из контракта было реализовано ровно один раз, а ошибки обработчика совпали с объявленными.
  3. Роутер. HttpApiBuilder.layer(todoApi).pipe(Layer.provide(todoHandlersLayer)) регистрирует маршруты, затем HttpRouter.serve(api) превращает их в HTTP-приложение.
  4. Порт. NodeHttpServer.layer(createServer, { port }) из @effect/platform-node, и запуск: NodeRuntime.runMain(Layer.launch(app)).
const api = HttpApiBuilder.layer(todoApi).pipe(Layer.provide(todoHandlersLayer))
const app = HttpRouter.serve(api).pipe(
  Layer.provide(Layer.merge(TodoRepository.layerMemory, TodoIdGenerator.layer)),
  Layer.provide(NodeHttpServer.layer(createServer, { port })),
)
NodeRuntime.runMain(Layer.launch(app))

2. Что происходит с одним запросом

Модуль HttpApiBuilder описывает себя одной фразой: «декодирует части запроса схемами, вызывает зарегистрированный обработчик и кодирует успех или объявленную ошибку в ответ» (HttpApiBuilder.ts, заголовок модуля). Ниже это можно прогнать по шагам. Переключатель схемы payload воспроизводит ловушку, в которую мы попали на шаге 1: Title вместо Schema.String.

Выбери запрос и нажми «Отправить».

Предскажи, потом проверь:

  1. POST /todos с пустым заголовком при обеих схемах payload. При Schema.String до обработчика доходит строка, домен возвращает EmptyTitle, и клиент увидит именно этот тег. При Title запрос отсекается на декодировании, тег будет общий, а объявленные в контракте ошибки становятся недостижимыми.
  2. POST /todo с опечаткой в пути. Ответ 404 приходит от роутера, а не от домена: TodoNotFound там нет.
  3. DELETE существующего todo. Поле success не объявлено, поэтому ответ 204 без тела.

3. Три ловушки, в которые мы уже наступили

  • Статус живёт на схеме, которую передали в error. HttpApiSchema.status(400) на членах Schema.Union игнорируется: библиотека читает аннотацию с самого объединения. Поэтому либо Schema.Union([...]).pipe(HttpApiSchema.status(400)), либо массив схем в error, каждая со своим статусом. Тест todoApi.test.ts это фиксирует через OpenApi.fromApi.
  • Тело запроса — схема, а не запись полей. Для методов с телом payload принимает только Schema: Schema.Struct({ title: Schema.String }). Запись { title: Schema.String } годится для params, но не для payload.
  • Зависимости обработчиков подаются после serve, сами обработчики до. TodoRepository нужен не при сборке слоя, а на каждый запрос, поэтому HttpApiBuilder.group записывает его в тип как требование на запрос, HttpRouter.Request<"Requires", …>. Сигнатура serve снимает эту обёртку и выставляет обычное требование слоя (HttpRouter.ts, serve). Если подать обработчики после serve, обёртка остаётся, и runMain не примет эффект.

4. Тест без сети

HttpApiTest.groups(todoApi, ["todo"]) собирает клиент, который вызывает обработчики напрямую, минуя сокеты, но проходя через те же схемы. Ему нужны слой обработчиков, сервисы и HttpServer.layerServices, а сам вызов оборачивается в Effect.scoped. Проверка того же круга через настоящий сервер: NodeHttpServer.layerTest поднимает сервер на свободном порту и даёт HttpClient к нему.
