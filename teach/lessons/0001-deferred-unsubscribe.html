Почему реестр атомов ждёт одну задачу, прежде чем разобрать атом

Один конкретный результат: после урока ты смотришь на любую последовательность «смонтировали, размонтировали, смонтировали снова» и говоришь, выполнятся ли acquire и release, не запуская код.

Связь с проектом: это ровно тот вопрос, который остался открытым после шага 5 фазы 7. Ресурс здесь — обработчик события storage внутри todosSyncAtom, а монтирование — useAtomMount в useTodoList.

1. Вопрос на обычном JavaScript

На минуту забудем про Effect. Любая библиотека, которая делит один ресурс между несколькими потребителями, держит счётчик. Первый потребитель создаёт ресурс, последний уничтожает. Вся идея в двенадцати строках:

let subscribers = 0
let handler = null

function subscribe() {
  subscribers += 1
  if (handler === null) {
    handler = () => invalidate("todos")
    window.addEventListener("storage", handler)   // acquire
  }
  return function unsubscribe() {
    subscribers -= 1
    if (subscribers === 0) teardown()             // а когда именно?
  }
}

Весь урок про комментарий в последней строке. Честных ответа два.

Ответ А: разобрать прямо сейчас

function teardown() {
  window.removeEventListener("storage", handler)  // release
  handler = null
}

Просто и предсказуемо. Каждая отписка, доводящая счётчик до нуля, оплачивает release, а следующая подписка снова оплачивает acquire.

Ответ Б: разобрать одной задачей позже, если ресурс всё ещё никому не нужен

let checkScheduled = false

function teardown() {
  if (checkScheduled) return
  checkScheduled = true
  setTimeout(() => {                 // «следующая задача»
    checkScheduled = false
    if (subscribers === 0) {         // всё ещё никого? тогда правда освобождаем
      window.removeEventListener("storage", handler)
      handler = null
    }
  }, 0)
}

Именно так устроен реестр атомов в Effect. В файле AtomRegistry.js отписка вызывает scheduleNodeRemoval, тот ставит задачу с задержкой 0, а задача перед удалением проверяет node.canBeRemoved. Таймаута простоя у runtime.atom по умолчанию нет, поэтому «позже» означает следующую задачу, а не секунды.

2. Прогони оба ответа сам

Панель ниже — ответы А и Б рядом. Mount — то, что делает useAtomMount, когда список появляется, Unmount — его очистка, Следующая задача даёт запланированной проверке выполниться. Кнопка Коммит StrictMode делает то же, что React в dev-режиме: setup, cleanup, setup, всё внутри одного коммита, до того как любая задача успеет выполниться.

подписчиков 0 живых обработчиков на window 0 проверка запланирована нет

3. Почему библиотеки выбирают ответ Б

  
У ответа А три цены, и каждая проявляется в настоящих приложениях. Каждая из них — причина подождать.

  
    
    
  • Пересоздать ресурс не бесплатно. Обработчик события дёшев. WebSocket, уже летящий fetch или подписка на серверный поток — нет. Освободить и тут же получить заново в пределах одной миллисекунды значит выбросить эту работу.
    • 
    
  • Состояние сбрасывается в «начальное». Разобранный эффект-атом теряет свой AsyncResult. При новом монтировании UI на миг показывает «загрузка» для данных, которые секунду назад были. TanStack Query решает ровно эту проблему: когда последний наблюдатель размонтируется, кэш не удаляется, а запускается таймер gcTime, по умолчанию пять минут, и он отменяется, если компонент успевает смонтироваться снова (TanStack Query: Caching).
    • 
    
  • Фреймворки размонтируют и монтируют нарочно. StrictMode в React выполняет «один дополнительный цикл setup+cleanup в dev-режиме для каждого эффекта», чтобы вскрыть отсутствующую очистку (React: StrictMode). Suspense, смена key и условный рендер делают похожее и в продакшене. Библиотека, разбирающая ресурс синхронно, платит за каждый такой случай.
    • 
  

  
Отложить на одну задачу — минимальное ожидание, при котором все случаи «размонтировали и смонтировали в одном коммите» становятся бесплатными, а освобождение всё равно происходит быстро, если потребитель действительно ушёл. У RxJS та же ручка: share({ resetOnRefCountZero }) принимает фабрику-уведомитель именно для «условного или отложенного сброса», когда подписчиков стало ноль (RxJS: share).


  
4. А что со StrictMode в твоём коде?

  
Реестр прячет двойной цикл StrictMode от атомов. От обычного useEffect с addEventListener он его не прячет: там очистка выполняется синхронно, и отсутствующая очистка видна как удвоенный обработчик при первой же загрузке страницы. Это тот баг, ради которого StrictMode существует, и совет React — чинить очистку, а не подавлять второй запуск (React: Synchronizing with Effects). Выключенный StrictMode убирает сигнализацию, а не утечку.
